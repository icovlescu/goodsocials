# GoodSocials v2 at /v2

v2 is the pivot product: the member's own AI chat writes through the MCP
connector, the free tier is the way in, and GoodSocials keeps the brand, the
business data, the board and the publishing. It is this same repository built
with one variable, `NEXT_PUBLIC_BASE_PATH=/v2`, as a second Vercel project.
`docs/MCP-CONNECTOR.md` describes the connector, the tiers and the platforms.

## What the base path changes

| | v1 (`NEXT_PUBLIC_BASE_PATH` unset) | v2 (`/v2`) |
|---|---|---|
| Landing page | The LinkedIn manager page | `components/marketing/pivot-landing.tsx` |
| Every route | `/board`, `/api/mcp`, … | `/v2/board`, `/v2/api/mcp`, … |
| Auth.js | `/api/auth`, `authjs.*` cookies | `/v2/api/auth`, `__Secure-gs-v2.*` cookies |
| OAuth issuer | `https://host` | `https://host/v2` |
| Connector URL | `https://host/api/mcp` | `https://host/v2/api/mcp` |
| Canonical links | `https://goodsocials.co/…` | `https://goodsocials.co/v2/…` |

`lib/base-path.ts` holds `BASE_PATH`, `withBase()` for anything Next does not
prefix by itself (plain anchors, browser `fetch`, manifest icons, metadata) and
`siteUrl()` for absolute URLs that leave the app (OAuth metadata, LinkedIn and
Stripe return addresses, the connector URL). `isPivot()` switches the landing
page and is also on with `NEXT_PUBLIC_EDITION=v2`.

## Running without the AI keys

The free tier works with no `ANTHROPIC_API_KEY` and no `OPENROUTER_API_KEY`.
`serverWriting()` and `serverImages()` in `lib/flags.ts` decide:

- Onboarding shows one screen instead of the funnel: add the connector, paste
  one message, and the member's chat reads the site and calls `set_up_brand`
  (principles, themes, goal, cadence). The board opens when it has.
- On the board, Approve on an idea, Revise, More ideas and the automatic draft
  top up say that the chat writes on this plan instead of calling a model.
- Approve on a draft schedules it without an image.
- The quality gate runs the rules in code only; the editor pass needs the key.

Adding the keys later turns each of those back on with no other change, which
is the paid tier.

## The deployment on Iulian's Vercel team

Two projects from the same repository and the same `main` branch:

| Project | Base path | Address |
|---|---|---|
| `goodsocials` | none | `https://goodsocials.vercel.app` |
| `goodsocials-v2` | `/v2` | `https://goodsocials-v2.vercel.app/v2`, and `https://goodsocials.vercel.app/v2` through the rewrite |

Environment on `goodsocials-v2`:

| Name | Value |
|---|---|
| `NEXT_PUBLIC_BASE_PATH` | `/v2` |
| `PUBLIC_ORIGIN` | `https://goodsocials.vercel.app` (the host members see; makes return URLs stay on it) |
| `AUTH_URL` | `https://goodsocials.vercel.app/v2/api/auth` |
| `AUTH_SECRET`, `TOKEN_ENCRYPTION_KEY`, `CRON_SECRET`, `LINKEDIN_DEBUG_SECRET`, `TEST_LOGIN_PASSWORD`, `LINKEDIN_API_VERSION`, `NEXT_PUBLIC_PAYMENTS_HIDDEN` | Same as `goodsocials` |
| `DATABASE_URL`, `DATABASE_URL_UNPOOLED` | From the Neon store, connected to both projects |

Environment on `goodsocials`: `V2_ORIGIN=https://goodsocials-v2.vercel.app`.
With it set, `next.config.ts` rewrites `/v2/*` and the two root OAuth
discovery paths (`/.well-known/oauth-authorization-server/v2`,
`/.well-known/oauth-protected-resource/v2/*`) to the v2 project.

One database for both is deliberate: an account is the same account on v1 and
v2, and v1's daily publish cron publishes the whole queue, v2 posts included.
v2's own copy of the cron calls `/api/cron/publish` without the base and finds
nothing, which is harmless.

### The database

The Vercel API cannot install the Neon integration on a team: the first store
needs the terms accepted in the dashboard. Once:

1. Vercel dashboard, team `covlescumihai-9118`, **Storage**, **Create Database**, **Neon**, free plan, region Frankfurt (`fra1`, next to the functions).
2. Connect it to `goodsocials` and to `goodsocials-v2`, all environments. Vercel adds `DATABASE_URL` and `DATABASE_URL_UNPOOLED`.
3. Redeploy both. Every build runs the migrations first
   (`scripts/migrate-on-build.ts`, the first half of `npm run build`), so the
   tables exist before the new deployment serves a request. The two builds share
   the database and take turns on an advisory lock; the second finds nothing to do.

### The admin pages

`/admin`, `/api/admin/health`, `/api/admin/migrate` and
`/api/admin/restart-onboarding` open for an admin session. On a database with no
admin yet, sign in (LinkedIn, or the test account) and open `/admin` (or
`/v2/admin`): it shows one button, **Make this account the admin**. The first
member to press it is the admin. The `admin_member` table stores a SHA-256 of
the member id and nothing else, so no email or id is in the code or the
database. Claim it straight after connecting the database, before sharing the
link, since the first claim wins. `?k=<LINKEDIN_DEBUG_SECRET>` still opens the
`/api/admin` routes for a script. To hand admin to another account later, for
example from the test account to a LinkedIn one, delete the row in the Neon
console and claim again.

### Testing the free tier end to end

1. Open `https://goodsocials.vercel.app/v2`, press **Start free**, sign in with
   the test account password. Then open `/v2/admin` once and claim it, so the
   health page opens for you. Sign in uses the test password (`TEST_LOGIN_PASSWORD`; LinkedIn sign in needs
   `LINKEDIN_CLIENT_ID` and `LINKEDIN_CLIENT_SECRET`, which are not set yet).
2. The setup screen shows the connector URL. In Claude, add it as a custom
   connector, press Connect, sign in with the same test password, Allow.
3. Paste the setup message with a website. Claude calls `set_up_brand`.
4. Ask for a post. Claude saves it with `create_draft`; it shows in Draft.
5. Ask to schedule it. The test account never sends anything to LinkedIn, so
   the publish run pauses it with "This is a test account" instead of posting.
6. Ask for an X version and a share link. The link opens X with the text in it.

## Putting it at goodsocials.co/v2

`goodsocials.co` belongs to the `pavelk2/goodsocials` Vercel project, which this
work never touches. Serving v2 there is one change on that side, by whoever
owns the domain:

1. **The rewrite.** Either deploy a `main` that includes this repo's
   `next.config.ts` and set `V2_ORIGIN=https://goodsocials-v2.vercel.app` on
   that project, or add the same rules to its own config:

   ```json
   {
     "rewrites": [
       { "source": "/v2", "destination": "https://goodsocials-v2.vercel.app/v2" },
       { "source": "/v2/:path*", "destination": "https://goodsocials-v2.vercel.app/v2/:path*" },
       { "source": "/.well-known/oauth-authorization-server/v2", "destination": "https://goodsocials-v2.vercel.app/v2/.well-known/oauth-authorization-server" },
       { "source": "/.well-known/oauth-protected-resource/v2/:path*", "destination": "https://goodsocials-v2.vercel.app/v2/.well-known/oauth-protected-resource/:path*" }
     ]
   }
   ```

2. **On `goodsocials-v2`**, change `PUBLIC_ORIGIN` to `https://goodsocials.co`
   and `AUTH_URL` to `https://goodsocials.co/v2/api/auth`, then redeploy.
3. **LinkedIn**, if LinkedIn sign in is used on v2: add
   `https://goodsocials.co/v2/api/auth/callback/linkedin` and
   `https://goodsocials.co/v2/api/linkedin/callback` to the app's authorized
   redirect URLs in the LinkedIn developer portal.
4. **Stripe**, if billing is on for v2: nothing new for checkout (return URLs
   follow `PUBLIC_ORIGIN`). The webhook stays at `goodsocials.co/api/stripe/webhook`
   when both share a database.

No DNS change is needed: the domain keeps pointing where it does, and only
`/v2` paths are passed through. Without step 1, v2 still runs at
`goodsocials.vercel.app/v2`.
